# 305名LLM用户＋277名规则用户：合并总表与接入方案

日期：2026-10-18。用户已提出305／277混合结构；具体ID分配为可审阅草案。已生成材料，未实施provider或运行模拟。

## 1. 现在只读哪一份

构建agent读取 [混合Agent总表_582.json](./混合Agent总表_582.json) 和本说明即可。总表内嵌身份、账户资料、来源行号、质量标记、每个LLM用户的固定提示词、动态输入模板，以及规则用户的候选概率参数，不再要求连接305份与582份两个文件。

人阅读时先看 [混合总表预览](./混合总表预览.md)。旧分拆文件仅作来源追溯；此前582人全部借用账户资料的草案退出本方案，不与本总表同时导入。

JSON用于保留嵌套资料与多行prompt，是本项目的可移植数据合同，不是宣称可直接通过SocioVerse2原生schema。构建agent仍需作字段映射。

| 原有分组 | LLM用户 | 规则用户 | 合计 |
|---|---:|---:|---:|
| 关注原帖发布者 | 43 | 39 | 82 |
| 不关注原帖发布者 | 262 | 238 | 500 |

305份账户资料各使用一次，没有重复借用。277名规则用户仍是合成用户，不假称为原数据中未评论的真人。六份属性重复待核查的资料仍各对应一个LLM用户，但不将可疑属性输入模型；另一个账户冲突的发博数量字段也继续隐藏。

43／262是按两组人数比例分配后取整数的建议，避免把关注者全设为LLM、非关注者全设为规则。组内用固定哈希排序选择ID，再与305份资料一一配对；方法和固定字符串写在总表assignment中。没有从真实数据发现这项类型分配。

账户资料只能支持账户属性，不自动支持真实信任、人格或行为参数。原始账户是否关注发布者尚未知；82／500仍是实验身份。保留原模拟ID，不意味着这些ID等于真实账号。

## 3. 平台每轮怎么执行

```text
同一个网络、同一套展示规则和政府排程
                   ↓
环境为每个用户生成本轮实际观察
                   ↓
读取总表 decision_mode
        ┌──────────┴──────────┐
      llm                    rule
  固定prompt＋观察＋记忆       有效接触＋原概率规则
  调用LLM一次                 不调用LLM
        └──────────┬──────────┘
             统一行动记录
                   ↓
批量提交状态、评论和转发 → 下一轮可见 → 保存记录
```

必须双向产生传播后果：规则用户转发的原帖或纠正可以进入LLM用户的信息流；LLM用户转发的有效内容也可以成为规则用户的接触。不要让规则用户只有人数、没有行动后果，也不要自动给LLM用户更高活跃度、更多关注边或更高展示优先级。

两类用户都是普通模拟参与者。SOURCE与GOVERNMENT仍是额外角色，不计入582人。

## 4. 两类用户分别做什么

| 内容 | LLM用户 | 规则用户 |
|---|---|---|
| 相信判断 | 根据资料、可见内容及本人记忆生成 | 按已冻结的概率／状态合同执行 |
| 转发 | LLM决定是否及转发哪条内容 | 使用相应传播概率执行 |
| 自由评论 | 可以生成 | 首版不生成，不偷偷调用LLM代写 |
| 记忆 | 可读取本人允许的历史 | 保存规则状态与日志，不做语言推理 |
| 观察 | 仅环境实际展示内容 | 相同展示规则产生的有效接触；规则只使用规定字段 |

固定prompt已经逐人内嵌。运行时追加observation_text和memory_text，不能把原Excel中该用户对本事件的真实评论填入初始记忆。

规则用户参数来自此前保存的原稿概率表，每行包含三个PBd条件对应的PB／RC候选值。当前selected_scenario_id和GT仍为null，RF=0.6标为原稿值；没有擅自选择正式条件。多接触处理、概率精度和状态提交顺序须使用确认的共同合同，不能由构建agent自填。

## 5. 不能靠混合结构掩盖的接口问题

**规则用户不理解评论的语义。** 首版建议规则用户只对明确关联原帖或纠正的有效接触执行已有规则；自由评论可展示给LLM，但不自动改变规则用户的PB。这是一项行为能力差异，必须在报告中注明。

LLM输出的文本不能因为含有“官方”“辟谣”等字样就被程序当成真实纠正。程序使用可追溯的content_id、parent_id和来源角色识别转发链；自由生成的新主张、纠正判断或反讽评论，在没有明确编码规则时不进入规则用户的概率触发路径。

政府账号直接发送和普通用户转发纠正仍须保留不同来源标识。它们是否都触发GT、何时抽RF等若原合同未确定，就保持缺项。不能因为统一了Action格式就认为行为含义已经一致。

GT在规则模型中是接受概率；LLM中的来源线索或个人信任描述不是这个概率。不得用同一个“GT=0.6”声称两类用户接受倾向已对齐。首轮建议固定政府信息内容，分别报告两类响应；以后再设计明确的可比较操作。

PBd候选表只直接作用于规则用户；没有给LLM用户写入相同数值意味着它不再是全体用户共同的相信概率差异。不能沿用旧参数名称而隐藏作用范围变化。

## 6. SocioVerse2具体改什么

研究层使用一个人群读取器、一个共同环境和一个按decision_mode分派的决策实现。输出统一保存agent_id、tick、判断、评论、转发对象、决策类型及错误状态。官方架构允许研究实现PopulationProvider、EnvironmentProvider、DecisionModel和MetricCollector；本方案不要求改核心引擎。[官方架构](https://socioverse.fudan-disc.com/docs/concepts/architecture/)

构建agent依次完成：

1. 读取总表，检查582个ID唯一，305份资料只用一次，277名规则用户没有prompt或账户资料。
2. 将总表用户映射为平台Persona，保留decision_mode为内部调度字段，不把“你是LLM组”等实验标签灌入普通用户输入。
3. 环境统一生成观察；不要分别运行两个互不相连的世界。
4. 决策层分流：LLM组拼接prompt，规则组执行概率规则；LLM失败单独记录，不临时变成规则用户。
5. 将两类结果映射成共同Action并统一提交；失败重试不重复转发。
6. 分别验证LLM→规则、规则→LLM两条传播路径，以及当前轮新增内容不提前进入同轮观察。
7. 统计全体、按圈内外、按决策类型以及两者交叉的结果。规则没有“不确定”时，不把LLM的不确定简单归成不相信。

## 7. 我对这个方案的判断

这是可行的工程折中：不再重复借用账户资料；保留582人规模；较全员LLM减少调用。在每人相同决策机会的假设下，LLM用户数量下降277/582≈47.6%，但实际token与费用还受活跃度、记忆长度、重试和互动内容影响，不能保证节省同一比例。

混合LLM与规则用户有先例，例如HiSim采用LLM核心用户和规则普通用户；但不能据此证明本项目的305／277比例或人群划分合理。这里的比例来自可用账户资料数和保留原模型规模的选择。[Mou等，2024](https://arxiv.org/abs/2402.16333)

主要代价是两类用户的判断方式与评论能力不同，而且305份资料只来自参与评论／转发的人。不能把规则组命名为“真实沉默用户”，也不能将整体结果差异全部归因于提示词增强异质性。

最小检查建议：固定277名规则用户的ID与规则设置，仅在305名LLM用户中比较无个人属性、加入个人属性、再加记忆。这样检查的是相同混合系统内的属性与记忆作用。另可运行全规则基准；全LLM对照不是本次必做，也未自动执行。
