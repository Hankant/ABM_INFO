## 代码如何运行

1. cli.py 读取 JSON 配置、事件和画像，指定 provider。
2. core.initialize 构造 82/500 两组、固定出度关注网络、实验设定的特征和先验；runner.attach_donor_profiles 只附加公开账户计数字段。
3. core.build_feed 依据活跃概率、关注边、推荐概率、帖子寿命和重复读取限制选择实际暴露。直接投送可以让原本不活跃者收到信息。
4. core._make_view 提供可见帖子、此前分数和最近五个决策轮的记忆。provider 返回信念分数、动作、目标帖子、公开立场、评论和简短理由。
5. core.step 先收集全部决策再同步提交。新用户帖子下一轮可见；没有信息则不调用决策器，也不更新信念。
6. runner.execute 先运行完整无干预轨迹，再从干预前一轮快照创建分支。storage 保存逐轮压缩快照、状态哈希并导出数据。

## 判断和限制

- 这是已有可执行流程的 Python 仿真项目，测试覆盖同步更新、暴露边界、分支、指标、缓存、预算和恢复；测试通过不证明人的行为模拟有效。
- MockDecisionProvider 使用 view 和 call_identity 的哈希，在 20/50/80 中取分数，并选择动作，不理解信息语义。runner 又将 run_id 加入 call_identity，因此分支名变化本身就能改变 Mock 决策。不能把上表差值解释为纠正效果，也不能用 Mock 做干预有效性检验。
- HTTP 模式分支分别调用模型；相同模拟 seed 并不意味着不同分支共享完全相同的 LLM 随机输出。需要把这种模型采样差异纳入后续重复运行设计。
- 305 份画像被抽样赋给 582 个 Agent，包含重复画像模板。真实字段限于粉丝数、关注数、累计发博数；网络、信任、活跃概率、初始倾向均为设定，不能当作真实群体复原。
- 纠正文本是无外部证据的统一实验脚本；来源线索为虚拟核验记录。运行成功不确认原事件真假。
- 接受率以组内全部人为分母，包含未暴露者。解释时应同时看未暴露人数，避免混淆触达和判断变化。
- README 称不传 --config 时使用 config.py 默认值，但 cli.py 实际默认读取 config/research.json；文档需校正。本次未修改该文档。
- 当前单事件完整网格为 9 条母轨迹和 405 条分支。不能依据一次 API 探测就直接启动全网格；实际费用需要测量请求量和 token 使用。
- 每轮扫描累积帖子、深复制状态并保存完整快照，便于审计，但扩大人群、轮次和分支数前应先做性能与磁盘占用测量。

## 与总项目的关系

可借鉴网络、暴露记录、同步更新、决策器替换、快照、缓存和恢复。当前 LLM 主要扮演模拟人；总项目还需要独立实现并记录信息来源 LLM，以及传统搜索对照。这里的两组、直接投送和特定来源线索不应直接变成总项目的固定研究设定。

## 重跑

在项目目录用有效 Python 3.11+ 执行：

```powershell
python test_all.py
python run.py run --config config/research.json --event data/imported/event_052/event.json --provider mock --tg 50 --output outputs/code_review_20261013
```

同一输出目录会校验输入并恢复已有轨迹。Windows 可使用现有“开始离线验证.cmd”，其会优先寻找 Codex 随附 Python，并创建新输出目录。
